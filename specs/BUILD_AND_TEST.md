# AI Build-Test-Fix Loop Guide

This guide explains how an AI agent can run a repeatable **build → test → read logs → fix → rebuild → retest** loop for the PlayFab C SDK.

The SDK has multiple testable components: **PlayFab Core** (auth, entity), **PlayFab Services** (catalog, inventory, etc.), **PlayFab Game Save**, and **XSAPI** (Xbox Live Services). All use the same test harness architecture.

## Architecture Overview

### Integration Tests (GameTestController Harness)

```
┌─────────────────────────────────────────────────────┐
│  GameTestController (.NET 8 WinForms + CLI)         │
│  - Hosts WebSocket server                            │
│  - Loads and orchestrates scenario YAML files        │
│  - Supports headless mode for CI and AI agents       │
│  - Emits JSON and JUnit results                      │
└────────────┬────────────────────────────────────────┘
             │ WebSocket
   ┌─────────▼──────────────────────────┐
   │  GameTestAppWindows (C++ GDK app)  │
   │  - Connects as "DeviceA"           │
   │  - Command registry dispatches     │
   │    SDK calls (PF* / Xbl* APIs)     │
   │  - Returns ActionResult JSON       │
   └────────────────────────────────────┘
```

|-----------|-------------|-----------|

## Prerequisites

- Visual Studio 2022 with C++ Desktop and GDK workloads
- Microsoft GDK installed (for integration tests and GDK builds)
- .NET 8 SDK (for GameTestController)
- MSBuild on `PATH`
- Xbox Live test account configured in sandbox (for XSAPI tests)
- PlayFab title configured with valid `testTitleData.json` (for PlayFab service tests)
- **Xbox devkit and PC must be in the `XDKS.1` sandbox** (for game save and two-device tests that use PlayFab CustomID auth). Use `xbconfig SandboxId=XDKS.1 /x:<ip>` for Xbox and `xbox-sandbox XDKS.1` for PC. Mismatched sandbox causes silent `E_FAIL` from `PFAuthenticationLoginWithCustomIDAsync` with no HTTP traffic.
- **Both devices need a signed-in Xbox user** for two-device scenarios. On Xbox, ensure a user is signed in on the console. On PC, sign into Xbox App or Game Bar under the `XDKS.1` sandbox. The test apps log a startup warning if no user is available.
- **PC Windows app must be registered with `wdapp`** for XUser APIs to work. The test runner does this automatically, but for manual runs: `"C:\Program Files (x86)\Microsoft GDK\bin\wdapp.exe" register <path-to-GameTestAppWindows-output>`. Without registration, `XUserAddAsync` fails with `0x89245106` even when a user is signed in.
- The test runner (`Run-GameSaveXboxTests.ps1`) performs automatic **pre-flight checks** for sandbox and user configuration before launching tests. If any check fails, the script stops with clear remediation steps.

### NuGet: why the build script moves `NuGet.config` aside

`tests-build.ps1` renames the repo's `NuGet.config` to `NuGet.config.bak` for the duration of the
build and restores it in a `finally` block. **This is deliberate — don't "clean it up".**

The repo `NuGet.config` (auto-generated by the Gardener `CentralFeedServiceAdoptionPlugin`) does
`<clear />` and pins a single feed, `xbox_PublicPackages`. That feed requires an authenticated
session and returns **`401 (Unauthorized)`** on a dev box without one, which fails restore for the
`packages.config` projects (`Test\GameTestAppWindows`, `Test\PlayFabGameSaveManualGDKTestApp`,
`Test\PlayFabGameSaveUnitTests`). Moving it aside lets the machine-level
`%APPDATA%\NuGet\NuGet.Config` apply instead, which carries the `azure-default` mirror
(`packagefeedproxy.microsoft.io`) that resolves without an interactive login.

> ⚠️ **Never work around a NuGet failure by adding `-Source https://api.nuget.org/v3/index.json`.**
> `nuget.org` is **deliberately disabled machine-wide** — it is listed under
> `<disabledPackageSources>` in `%APPDATA%\NuGet\NuGet.Config` as a supply-chain-attack control, and
> the repo config's `<clear />` is intentional. Bypassing either defeats a security control that was
> added on purpose. Authenticate to the feed, or use the no-restore validation below.

Useful when diagnosing a restore failure:

| Symptom | Meaning |
|---|---|
| `Unable to load the service index for source ...xbox_PublicPackages...` + `Response status code does not indicate success: 401 (Unauthorized).` | No authenticated feed session. Expected outside CI; this is what moving `NuGet.config` aside avoids. |
| `This project references NuGet package(s) that are missing on this computer.` | Restore never succeeded. Fix restore — this is not a project-file bug. |
| `msbuild /t:Restore` → `Nothing to do. None of the projects specified contain packages to restore.` | `/t:Restore` only handles `PackageReference`. These projects use `packages.config`; restore with `nuget restore <packages.config> -PackagesDirectory <dir>`. |

### Validating a `.vcxproj` change without building

Build-configuration questions ("did my shared `.vcxitems` swap take effect?", "which `HC_PLATFORM`
is this actually compiling as?") can be answered by MSBuild **evaluation**, which needs no packages
and no compile:

```powershell
$msb = "C:\Program Files\Microsoft Visual Studio\2022\Enterprise\MSBuild\Current\Bin\MSBuild.exe"

# Evaluated ITEMS (what actually compiles) - respects Condition attributes:
& $msb <project.vcxproj> /p:Configuration=Debug /p:Platform=x64 /getItem:ClCompile /nologo

# Evaluated PROPERTIES:
& $msb <project.vcxproj> /p:Configuration=Debug /p:Platform=x64 /getProperty:HCEnableWebSocketCompression /nologo
```

> ⚠️ **Do not use `/pp` to decide which files compile.** `/pp` emits the *merged project XML* with
> `Condition` attributes **intact and unevaluated**, so every conditional `ClCompile` appears
> whether or not it is actually built — e.g. `websocketpp_websocket.cpp` shows up in `pp.xml` even
> when `HCEnableWebSocketCompression=false` conditions it out. Use `/getItem:ClCompile` for items
> and `/getProperty:<name>` for properties.

This confirms the real item list and property values. It does **not** validate compile or link.

When changing which `*.vcxitems` a project imports, update **both** the `<Import ... Label="Shared" />`
in the `.vcxproj` **and** the matching `...vcxitems*{project-guid}*SharedItemsImports = 4` line in
the `.sln`. Miss the `.sln` half and the shared project silently fails to resolve.

```yaml
id: pfcore-06-login-xuser
name: PFCore 06 - Login with XUser
tags:
  - pfcore
  - passing
devices:
  DeviceA: {}
defaults:
  stepTimeoutSeconds: 180
blocks:
  init:
    - command: XGameRuntimeInitialize
    - command: XTaskQueueCreate
    - command: XUserAddAsync
  test:
    - command: PFServicesInitialize
    - command: PFServiceConfigCreateHandle
    - command: PFAuthenticationLoginWithXUserAsync
  cleanup:
    - command: PFEntityCloseHandle
    - command: PFServicesUninitializeAsync

  - role: DeviceA
    block: init
  - role: DeviceA
    block: test
cleanup:
  DeviceA:
    - command: PFEntityCloseHandle
    - command: PFServicesUninitializeAsync
```

## Step-by-Step: AI Build-Test-Fix Loop

### Recommended Loop

```
Loop:
  1. Build:  Utilities\Scripts\tests-build.ps1
  2. Run:    py Utilities\Scripts\tests-run.py <suite> --stop-on-fail --start N
  3. If all pass → done
  4. Read logs in Out\logs\ (controller.log, Device*-stdout.txt)
  5. Fix first failure
  6. Set N = number of scenarios that passed before failure (to skip known-good ones)
  7. Go to 1
```

After local iteration succeeds, run a full pass (without `--stop-on-fail` or `--start`) before declaring success.

### Game Save Loop

```
Loop:
  1. Build:  Utilities\Scripts\gamesave-build.ps1
  2. Run:    py Utilities\Scripts\tests-run.py gamesave-inproc
  3. If all pass → done
  4. Read:   Utilities\Scripts\read-test-logs.ps1 -FailedOnly
  5. Fix first failure
  6. Go to 1
```

### XSAPI Loop (Cross-Repo)

When changing XSAPI source **and** testing via the harness:

1. Edit XSAPI source in `C:\git\XSAPI\Source\...`
2. Build XSAPI: `msbuild <solution> /p:Platform=Gaming.Desktop.x64 /p:Configuration=Debug`
3. Build test app: `C:\git\PlayFab.C\Utilities\Scripts\xsapi-build.ps1`
4. Run tests: `py C:\git\PlayFab.C\Utilities\Scripts\tests-run.py xsapi --only <N>`

## Common Failure Patterns

| Pattern | Likely Cause | Where to Inspect |
|---------|-------------|------------------|
| `E_INVALIDARG` / `0x80070057` | Missing or invalid parameter | Scenario YAML params + handler validation code |
| `HTTP_E_STATUS_*` | Service-side rejection | Device logs for HTTP request/response details |
| `E_PF_*` error codes | PlayFab service error | Device logs, PlayFab error code reference |
| Timeout waiting for device | Device app not running or failed to connect | Controller stderr + device startup logs |
| Build error: missing include | Submodules not initialized | `git submodule update --init --recursive` |
| NuGet `401 (Unauthorized)` on `xbox_PublicPackages`, or `references NuGet package(s) that are missing` | Repo `NuGet.config` pins an authenticated-only feed | See [NuGet: why the build script moves `NuGet.config` aside](#nuget-why-the-build-script-moves-nugetconfig-aside). Do **not** add `-Source nuget.org`. |
| `BUILD DID NOT COMPLETE` + `The term 'msbuild' is not recognized as a name of a cmdlet` | `tests-build.ps1` calls `msbuild` off `PATH`, which a plain PowerShell session does not have. The .NET stages succeed first, so this looks like a late failure. | Prepend it for the session: `$env:PATH = "C:\Program Files\Microsoft Visual Studio\2022\Enterprise\MSBuild\Current\Bin;$env:PATH"` (or run from a Developer PowerShell). |
| Xbox run times out at the prerequisite stage, last log line is `Launching AdminHelper (will trigger UAC)` preceded by `[TRACE] TryRunViaAdminHelper: pipe not available` | `AdminHelperTray` is not running, so each `EnableNetwork` falls back to a UAC-elevated launch that blocks forever unattended. Note the harness treats a merely `Disconnected` adapter (e.g. Wi-Fi with no network) as "Down — will re-enable", so this can fire on a perfectly healthy machine. | Start `Out\x64\Debug\AdminHelperTray\AdminHelperTray.exe` and approve the UAC prompt once; it then serves subsequent requests over its named pipe. Check with `Get-Process AdminHelperTray`. |
| Xbox run aborts with `Capturing ETL... FAILED` / `[WinError 2] The system cannot find the file specified` | ETL capture tooling (`xbdiagcap`/`xbcp`) is missing or not on `PATH`. Capture is ON by default and aborts the whole run. | Fix the tooling, or re-run with `--no-captureetl` when you only need pass/fail. |
| `E_PF_GAMESAVE_*` | Game save state error | Game save handler code + sync manager state |
| Crash in handler | Invalid state or null handle in test sequence | Device logs, handler file for the failing command |

## Tips for AI Agents

1. **Use `tests-build.ps1`** for the fastest path to a working test setup.
2. **Use `-Tag <component>`** to scope test runs to the component you're working on.
3. **Use `-Scenarios <N>`** to run a single scenario while debugging.
4. **Read device logs first** for integration failures — they contain the HRESULT and request details.
5. **Keep fixes surgical.** Don't refactor while triaging test failures.
6. **Rebuild after every code change** before retesting.
7. **Check the `passing`/`failing` tags** in scenarios — `failing` scenarios have known issues.
8. **Do not edit generated files** in `Source/PlayFabServices/Source/Generated/`. Edit templates and regenerate.
9. **Run a full pass** before declaring a change complete.
