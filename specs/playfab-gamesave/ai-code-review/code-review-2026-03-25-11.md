**Trigger scenario:** On the GRTS/GDK path, call `PFGameSaveFilesAddUserWithUiAsync` twice for the same `PFLocalUserHandle` without uninitializing first.

**What goes wrong:** The second call does not reject the duplicate add. It reuses the existing slot, closes only the duplicated `localUser` handle, and then overwrites `configHandle` without freeing the old `PFXGameSaveInitializeConfig` result. Each duplicate add leaks the previous config handle until process shutdown.

**Concrete fix:** Match the Win32 provider’s behavior: return `E_PF_GAMESAVE_USER_ALREADY_ADDED` unless this is an explicit offline reconnect path. If slot reuse must remain supported, free the old `configHandle` before nulling/overwriting it.

**Trigger scenario:** On the GRTS/GDK path, start `PFGameSaveFilesAddUserWithUiAsync`, let it reach `PFXPALCallGetFolderWithUiAsync`, then cancel it (`XAsyncCancel`) or cancel via the platform UI.

**What goes wrong:** The user slot is registered before `GetFolderWithUi` completes, but the cancel paths in `PFXPALGetFolderComplete` return `E_ABORT` without removing that slot or freeing the config. After the failed add, `GetFolder`, `GetFolderSize`, `UploadWithUiAsync`, and `SetSaveDescriptionAsync` all see a non-null state and treat the user as added even though add-user failed. That leaves stale state behind and can drive later operations against a half-initialized config.

**Concrete fix:** On every abort/user-cancel path after slot registration, close the duplicated `localUser`, free the `configHandle`, clear the slot, and only expose the slot to later APIs after `PFXGameSaveFilesGetFolderWithUiResult` succeeds.

**Trigger scenario:** Device A changes files under atomic unit `slot1` in the cloud. Before syncing, device B makes a **folder-only** local change under the same atomic unit (for example, creates or deletes an empty subfolder under `slot1`) and then runs `PFGameSaveFilesAddUserWithUiAsync`.

**What goes wrong:** Conflict detection only examines local file uploads/deletions. Local folder creates/deletes are ignored, so the SDK does not show conflict UI and silently performs a partial merge inside an atomic unit that is supposed to be all-or-nothing. The remote file changes are downloaded while the local empty-folder change is preserved/applied locally instead of forcing the user to choose local or remote.

**Concrete fix:** Extend `ScanForConflicts` to also check `GetFoldersToCreateUponUpload()` and `GetFoldersToDeleteUponUpload()` (or compute a unified set of locally changed top-level folders) against `topLevelFoldersNeedingDownload` before deciding that no conflict exists.
