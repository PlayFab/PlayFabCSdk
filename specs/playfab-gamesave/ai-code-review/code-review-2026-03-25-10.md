## Important Issues

### II-1: Data race on `internal_seed` in GUID generator

**File:** `Source\PlayFabGameSave\Source\Common\Utils.cpp:19-27`

`internal_seed` is a non-atomic, non-thread-local static global. `internal_rand()` reads and writes it without synchronization. `CreateGUID()` (which calls `internal_rand` 32 times) is called from multiple async work threads — for example, `UploadStep::CompressFiles`, `MergeLocalFolders`, and `GetLocalDeviceID` all call `CreateGUID()` and may execute on different task queue threads.

```cpp
static uint64_t internal_seed = 0;         // line 19: not atomic, not thread_local
uint32_t internal_rand(void)
{
    if (internal_seed == 0)
    {
        internal_seed = static_cast<uint64_t>(std::time(nullptr));  // race: two threads both see 0
    }
    internal_seed = internal_seed * LCG_MULTIPLIER + LCG_INCREMENT; // race: read-modify-write
    return (uint32_t)(internal_seed / LCG_MODULUS_DIVISOR) % LCG_MODULUS_RANGE;
}
```

**Trigger:** Two concurrent sync operations (e.g., AddUser for two local users, or concurrent upload + SetSaveDescription) both call `CreateGUID()`. The read-modify-write on `internal_seed` is a data race (C++ UB). In practice, two threads could read the same seed value and produce identical GUIDs for file IDs or zip file names, potentially causing upload collisions or data corruption.

**Fix:** Change `internal_seed` to `thread_local` (simplest fix — each thread gets its own sequence):
```cpp
static thread_local uint64_t internal_seed = 0;
```

### II-2: Data race on `m_isForcedDisconnectFromCloud` between poll worker and provider threads

**File:** `Source\PlayFabGameSave\Source\SyncManager\FolderSyncManager.h:53,54,98`

`m_isForcedDisconnectFromCloud` is a plain `bool` written by `ActiveDevicePollWorker::CheckActiveDevice()` (background task queue thread) and read by `DoWorkFolderUpload()` (async provider work thread) without synchronization. Each provider holds its own `m_folderSyncMutex` — these do NOT synchronize with the poll worker.

```cpp
// FolderSyncManager.h:53-54 — no synchronization
void SetForcedDisconnectFromCloud(bool isForcedDisconnectFromCloud) { m_isForcedDisconnectFromCloud = isForcedDisconnectFromCloud; }
bool IsForcedDisconnectFromCloud() const { return m_isForcedDisconnectFromCloud; }

// FolderSyncManager.h:98 — plain bool
bool m_isForcedDisconnectFromCloud{ false };
```

Writer — `ActiveDevicePollWorker.cpp:156`:
```cpp
folderSync->SetForcedDisconnectFromCloud(true);
```

Reader — `FolderSyncManager.cpp:514`:
```cpp
if (IsForcedDisconnectFromCloud())
{
    return E_PF_GAMESAVE_DISCONNECTED_FROM_CLOUD;
}
```

**Trigger:** `ActiveDevicePollWorker` detects another device took the lock (every 10 minutes) while an `UploadWithUiAsync` is in progress. The poll worker writes `true` on the background queue thread, while `DoWorkFolderUpload` reads on the provider thread. Per C++14/17, this is undefined behavior.

**Fix:** Change to `std::atomic<bool>`:
```cpp
std::atomic<bool> m_isForcedDisconnectFromCloud{ false };
```

### II-3: Data race on `UploadStep` state read by `SetSaveDescriptionProvider` across unsynchronized provider mutexes

**File:** `Source\PlayFabGameSave\Source\Providers\SetSaveDescriptionProvider.cpp:21-23`

`SetSaveDescriptionProvider` and `UploadAsyncProvider` each have their own `m_folderSyncMutex` member. These are separate mutex instances that do NOT synchronize access to the shared `FolderSyncManager` (and its `UploadStep`) across the two providers. `SetSaveDescriptionProvider::DoWork` reads `m_folderSync->HasStartedFinalizeManifest()` which accesses `UploadStep::m_hasStartedFinalizeManifest` (a plain `bool`), while `UploadAsyncProvider::DoWork` writes it via `UploadStep::Upload()` on a different thread.

```cpp
// SetSaveDescriptionProvider.cpp:21-23 — reads UploadStep state
FolderSyncManagerProgress prog = m_folderSync->GetSyncProgress();  // protected by m_progressMutex (OK)
if ((prog.syncState == PFGameSaveFilesSyncState::Uploading || ...) &&
    m_folderSync->HasStartedFinalizeManifest())  // reads UploadStep::m_hasStartedFinalizeManifest (NOT synchronized)
```

```cpp
// UploadStep.cpp:693-695 — writes m_hasStartedFinalizeManifest on UploadAsyncProvider's thread
if (!m_hasStartedFinalizeManifest)
{
    m_hasStartedFinalizeManifest = true;
}
```

**Trigger:** Call `PFGameSaveFilesSetSaveDescriptionAsync` while `PFGameSaveFilesUploadWithUiAsync` is in the `FinalizeManifest` stage. The SetSaveDescriptionProvider may read a stale `false` for `m_hasStartedFinalizeManifest`, bypassing the finalize-wait logic. It then calls `UpdateManifest` on the pending manifest version while `FinalizeManifest` is in-flight on the same version, potentially causing a service error or silent description loss.

**Fix:** Change `m_hasStartedFinalizeManifest` in `UploadStep` to `std::atomic<bool>`:
```cpp
// UploadStep.h — change from:
bool m_hasStartedFinalizeManifest{ false };
// to:
std::atomic<bool> m_hasStartedFinalizeManifest{ false };
```

## Minor Issues

### MI-1: `PFGameSaveFilesSetMockRootFolderForDebug` missing null check — crash on null input

**File:** `Source\PlayFabGameSave\Source\Api\PFGameSaveFilesAPI.cpp:277-283`

The `rootFolder` parameter is annotated `_In_` (non-optional) but is not null-checked before being passed to `SetDebugRootFolderOverride()`, which constructs a `std::string` from the pointer. Passing `nullptr` is undefined behavior and will crash.

```cpp
PF_API PFGameSaveFilesSetMockRootFolderForDebug(_In_ const char* rootFolder)
{
    return GSApiImpl("PFGameSaveFilesSetMockRootFolderForDebug", [&](GameSaveGlobalState& state) {
        state.SetDebugRootFolderOverride(rootFolder);  // crash if rootFolder == nullptr
        return S_OK;
    });
}
```

**Trigger:** Call `PFGameSaveFilesSetMockRootFolderForDebug(nullptr)`.

**Fix:** Add null validation:
```cpp
RETURN_HR_INVALIDARG_IF_NULL(rootFolder);
```

### MI-2: `s_debugForceChange` never reset — causes infinite offline-forcing loop in debug builds

**File:** `Source\PlayFabGameSave\Source\SyncManager\ActiveDevicePollWorker.cpp:152`

Once `PFGameSaveFilesSetActiveDevicePollForceChangeForDebug()` sets `s_debugForceChange = true`, every subsequent poll (every 10 minutes) will trigger the active-device-changed callback and force `SetForcedDisconnectFromCloud(true)`. The flag is never reset to `false`.

```cpp
if (deviceIdChanged || ActiveDevicePollWorker::s_debugForceChange)  // line 152
{
    folderSync->SetForcedDisconnectFromCloud(true);
    // ... triggers callback
    // s_debugForceChange is never reset!
}
```

**Trigger:** In a debug build, call `PFGameSaveFilesSetActiveDevicePollForceChangeForDebug()`. Every subsequent 10-minute poll fires the callback and disconnects from cloud, even if the user reconnects.

**Fix:** Reset the flag after use:
```cpp
if (deviceIdChanged || ActiveDevicePollWorker::s_debugForceChange)
{
    ActiveDevicePollWorker::s_debugForceChange = false;  // reset after triggering
    folderSync->SetForcedDisconnectFromCloud(true);
    // ...
}
```
